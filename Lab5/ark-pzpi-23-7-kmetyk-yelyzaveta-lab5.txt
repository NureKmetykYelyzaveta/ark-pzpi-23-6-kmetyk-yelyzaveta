      Мета роботи
       Метою роботи було розгорнути серверну частину вебзастосунку на хостингу Render, налаштувати роботу з базою даних SQLite у розгорнутому середовищі, а також реалізувати IoT-модуль у вигляді симуляції пристрою в Wokwi (ESP32 + датчики) та інтегрувати його з бекендом через REST API для передачі телеметрії. Додатковою метою було перевірити роботу API через Swagger, включно з авторизацією користувачів і окремою авторизацією для IoT-пристроїв за ключем.
      
      Хід роботи
      5.1. Використання SQLite у розгорнутій системі
      Для зберігання даних застосунку використовувалась SQLite-база (./db/pet_shelter.db), яка ініціалізується при старті сервера. Під час запуску бекенду виконувались створення таблиць (через CREATE TABLE IF NOT EXISTS) та заповнення тестовими даними через seed-скрипт. Окремо для IoT частини була додана таблиця DeviceTelemetry, у яку записуються телеметричні дані пристрою: ідентифікатор пристрою (DeviceGuid), посилання на тварину (DogId), температура, рівень руху, прапорці тривоги та час створення. Це дозволило зберігати історію вимірювань і отримувати останній запис або список записів за конкретним пристроєм через API. Під час розгортання враховувалась особливість SQLite: файл бази зберігається локально для інстансу сервера. Тому для демонстрації коректної роботи використовувалась ініціалізація й seed при запуску, а також перевірка наявності потрібних таблиць і колонок.

      5.2. Розгорнута Backend-частина
      Бекенд реалізовано на Node.js + Express. Сервіс був розгорнутий на Render, де налаштовано запуск через npm start. Для перевірки доступності системи використано кореневий маршрут, що повертає повідомлення “Pet Shelter API is running”. Також було підключено Swagger UI для тестування API через браузер (/api-docs) і окремий маршрут swagger.json, який додає коректний servers.url на основі поточного домену Render. Авторизація користувачів виконувалась через JWT: після логіну сервер видає токен, який використовується для доступу до захищених маршрутів. Для демонстрації роботи системи створювався користувач, створювалась тварина та для неї створювався запис SmartDevice (розумний пристрій) з унікальним DeviceGuid. Через Swagger проводилась перевірка CRUD-операцій і доступу з токеном.

      5.3. IoT-модуль (симуляція у Wokwi) та інтеграція з бекендом 
      IoT-модуль реалізовано як симуляція ESP32 у Wokwi. У прошивці використовувались: датчик температури DS18B20 (через OneWire/DallasTemperature), інерційний датчик MPU6050 для оцінки активності/руху, а також OLED-дисплей SSD1306 для відображення поточних значень. Пристрій підключається до мережі Wi-Fi (Wokwi-Guest) і кожні ~2 секунди збирає показники: температуру та “motion level” (обчислення за вектором прискорення). Далі формується JSON-запит і виконується POST. Для захисту IoT-ендпоінтів застосовано окремий механізм авторизації: пристрій надсилає заголовок X-Device-Key, який на сервері перевіряється з process.env.IOT_DEVICE_KEY. Це дозволяє відокремити доступ IoT-пристроїв від доступу користувачів по JWT. Під час інтеграції була врахована вимога узгодженості ідентифікатора пристрою: DeviceGuid, який прошитий у Wokwi-клієнті, має збігатися з DeviceGuid, створеним у таблиці SmartDevices, інакше сервер повертає Device not registered. Для тестування з боку бекенду телеметрія переглядалась через API GET /api/iot/telemetry/latest?deviceGuid=... та GET /api/iot/telemetry?deviceGuid=...&limit=....

Рисунок 3 – Симуляція IoT-пристрою в Wokwi (ESP32 з DS18B20, MPU6050 та OLED-дисплеєм) і вивід телеметрії в терміналі

      Окремо виявлено важливий момент при використанні Swagger: Swagger UI не відправляє IoT-заголовок автоматично, якщо в OpenAPI не описаний securityScheme типу apiKey. Тому для “робочого” тестування IoT через Swagger у swagger-конфіг було додано deviceKeyAuth (apiKey у header X-Device-Key) і на IoT-ендпоінтах вказано security: deviceKeyAuth. Після цього Swagger почав додавати потрібний заголовок у запити, що усунуло помилку 401 Invalid device key при тестуванні через Swagger.
      
      Висновки
       У результаті виконання роботи було успішно розгорнуто бекенд на Render та забезпечено роботу SQLite-бази у розгорнутому середовищі з ініціалізацією таблиць і тестовими даними. Реалізовано IoT-модуль у Wokwi з датчиками температури та руху і налаштовано передачу телеметрії на сервер через захищені REST-ендпоінти. Перевірено збереження телеметрії в базі та її отримання через API. Додатково було налаштовано коректне тестування IoT-ендпоінтів через Swagger шляхом додавання apiKey-авторизації для заголовка X-Device-Key. Отримані результати підтвердили працездатність повної інтеграції “пристрій → бекенд → БД → перегляд через API”, а також показали важливість правильного документування та передачі заголовків авторизації в Swagger при тестуванні.
