1 ОПИС ІНЖЕНЕРНИХ РІШЕНЬ
      1.1 Архітектурні рішення
      Під час розробки серверної частини програмної системи ShelterMonitor було застосовано модульно-шарову архітектуру з чітким розмежуванням відповідальностей між компонентами. Обраний підхід забезпечує розширюваність, гнучкість, простоту тестування та підтримки.
      У системі використано такі основні архітектурні патерни:
      Repository Pattern
      Доступ до даних здійснюється через централізовані модулі роботи з базою SQLite. Це дозволяє легко змінювати структуру БД та розширювати функціонал без впливу на інші частини системи.
      Middleware Pattern
      Використовується для авторизації запитів, перевірки JWT-токенів, а також для автоматичного оновлення активності користувача (LastActivity).
      Controller–Service–Repository підхід (адаптований під Express)
      • Controllers — приймають HTTP-запити та повертають відповіді.
      • Business Logic (services) — реалізує правила системи: створення пристроїв, перевірку прав доступу, блокування користувачів, формування статистики.
      • Database Layer — усі операції над БД виконуються через модуль db.js.
      Також використано:
      DTO Pattern
      Для прийому та повернення даних у форматах, безпечних для клієнта.
      JWT Authentication Pattern
      У системі реалізовано авторизацію на основі токенів. Кожен користувач отримує токен, що містить роль і ID, а сервер перевіряє:
      • валідність токена;
      • чи не заблокований користувач;
      • чи має він право виконувати дію.
      
      Взаємодія шарів системи
      1. Користувач надсилає HTTP-запит.
      2. Middleware auth перевіряє JWT токен.
      3. Контролер отримує запит та передає його у бізнес-логіку.
      4. Бізнес-логіка звертається до бази даних, виконує перевірки та правила.
      5. Результат повертається контролеру, який формує відповідь клієнту.
      Такий підхід знижує зв’язність і дає змогу легко розширювати функціонал (додавати нові модулі — аналітику, пристрої, медичні дані тощо).
      
      1.2 Вибір технологій та інструментів
      Нижче наведено перелік основних технологій, використаних у серверній частині.
      Таблиця 1.1 — Основні технології, використані у ShelterMonitor
      Технологія      Призначення      Node.js      Серверна платформа виконання      Express.js      Фреймворк для створення RESTful API      SQLite      Легка вбудована база даних      JWT (JSON Web Token)      Механізм аутентифікації та авторизації      BCrypt      Хешування паролів користувачів      CORS      Контроль доступу між доменами      Swagger / OpenAPI      Документація та тестування API      dotenv      Зберігання секретів та конфігурацій      Swagger-UI      Візуальна взаємодія з API      
      Обґрунтування вибору технологій:
      • Express.js — мінімалістичний, швидкий фреймворк, ідеально підходить для REST-сервісів.
      • SQLite — не потребує серверного розгортання, легко переноситься, швидка у використанні.
      • JWT — дозволяє зберігати інформацію про користувача всередині токена, що робить систему статeless.
      • Swagger — значно полегшує демонстрацію роботи API та є обов’язковим компонентом лабораторної роботи.
      • bcrypt.js — безпечне хешування паролів користувачів.
      • dotenv — приховує секрети (наприклад, JWT_SECRET).
      
      1.3 Реалізована бізнес-логіка
      Бізнес-логіка ShelterMonitor охоплює кілька доменних областей.
      
      Управління розумними пристроями (SmartDevices)
      Основні функції:
      • створення пристрою та прив’язка його до тварини;
      • оновлення координат пристрою;
      • перевірка власника пристрою;
      • отримання списку пристроїв користувача.
      Бізнес-правила:
      • пристрій може належати лише одній тварині;
      • користувач може керувати лише пристроями своїх тварин;
      • адміністратор має доступ до всіх пристроїв;
      • початковий рівень заряду — 100%.
      Алгоритм створення пристрою:
      1. Знайти тварину за ID.
      2. Перевірити, чи належить вона користувачу.
      3. Перевірити, чи не існує вже пристрій із таким DogId.
      4. Створити новий запис SmartDevice.
      5. Повернути ID створеного пристрою.
      
      Управління користувачами
      Основні функції:
      • реєстрація та логін;
      • збереження активності (LastActivity);
      • блокування та розблокування користувачів;
      • підтримка ролей: Admin / User.
      Бізнес-правила:
      • заблокований користувач не може виконувати дії;
      • кожен запит оновлює поле LastActivity;
      • адміністратор не може бути заблокований іншим адміністратором;
      • email має бути унікальним.
      
      Адміністративний модуль
      Адміністратор може:
      • блокувати/розблоковувати користувачів;
      • переглядати журнал дій;
      • отримувати статистику користувачів:
      o загальна кількість,
      o активні за місяць,
      o заблоковані,
      o розподіл за ролями.


2 ФРАГМЕНТИ ПРОГРАМНОГО КОДУ
      У цьому розділі наведено приклади основних частин бізнес-логіки та адміністративних функцій серверної частини програмної системи ShelterMonitor.
Фрагменти коду демонструють ключові алгоритми, реалізовані у сервісах, а також механізми взаємодії системи з базою даних через ORM-моделі.
      
      2.1 Бізнес-логіка: створення пристрою
       router.post("/", (req, res) => {
           const { deviceGuid, dogId } = req.body;
       
           db.get("SELECT UserId FROM Animals WHERE Id=?", [dogId], (err, dog) => {
               if (!dog) return res.status(404).json({ message: "Dog not found" });
       
               const userId = req.user.id;
               if (dog.UserId != userId)
                   return res.status(403).json({ message: "Not your dog" });
       
               db.get("SELECT * FROM SmartDevices WHERE DogId=?", [dogId], (err, exist) => {
                   if (exist) return res.status(400).json({ message: "Device already exists" });
       
                   db.run(
                       `INSERT INTO SmartDevices (DeviceGuid, DogId, LastLatitude, LastLongitude, BatteryLevel)
                        VALUES (?, ?, 0, 0, 100)`,
                       [deviceGuid, dogId],
                       function () {
                           res.status(201).json({ id: this.lastID });
                       }
                   );
               });
           });
       });
      
      2.2 Оновлення пристрою
       router.put("/:id", (req, res) => {
           const { LastLatitude, LastLongitude, BatteryLevel } = req.body;
           const userId = req.user.id;
       
           db.get("SELECT DogId FROM SmartDevices WHERE Id=?", [req.params.id], (err, dev) => {
               if (!dev) return res.status(404).json({ message: "Device not found" });
       
               db.get("SELECT UserId FROM Animals WHERE Id=?", [dev.DogId], (err, dog) => {
                   if (dog.UserId != userId)
                       return res.status(403).json({ message: "Not your device" });
       
                   db.run(
                       "UPDATE SmartDevices SET LastLatitude=?, LastLongitude=?, BatteryLevel=? WHERE Id=?",
                       [LastLatitude, LastLongitude, BatteryLevel, req.params.id],
                       () => res.json({ message: "Updated" })
                   );
               });
           });
       });
      
      2.3 Адміністрування — блокування користувача
       router.post("/block/:id", (req, res) => {
           const { reason } = req.body;
       
           db.get("SELECT RoleId FROM Users WHERE Id=?", [req.params.id], (err, user) => {
               if (!user) return res.status(404).json({ message: "User not found" });
               if (user.RoleId === 1) return res.status(403).json({ message: "Cannot block admin" });
       
               db.run(
                   "UPDATE Users SET IsBlocked=1, BlockReason=? WHERE Id=?",
                   [reason, req.params.id],
                   () => res.json({ message: "User blocked" })
               );
           });
       });
      
      2.4 Отримання статистики користувачів
       router.get("/statistics", (req, res) => {
           db.all("SELECT * FROM Users", [], (err, users) => {
               const now = Date.now();
               const monthAgo = now - 30 * 24 * 60 * 60 * 1000;
       
               const stats = {
                   totalUsers: users.length,
                   activeUsers: users.filter(u => new Date(u.LastActivity).getTime() >= monthAgo).length,
                   blockedUsers: users.filter(u => u.IsBlocked === 1).length,
                   admins: users.filter(u => u.RoleId === 1).length,
                   regularUsers: users.filter(u => u.RoleId === 2).length
               };
               res.json(stats);
           });});
3 UML ДІАГРАМИ
3.1 UML діаграма діяльності
      Створення розумного пристрою (SmartDevice)
      Покроковий опис логіки, зображеної на діаграмі:
      Початок (ініціація):
      Користувач має у своєму профілі тварину та бажає прив’язати до неї розумний пристрій. Для цього він надсилає POST-запит до API:
POST /api/smart-devices.
      1. Запит до API
      Користувач передає у запиті:
      • deviceGuid — унікальний ідентифікатор пристрою,
      • dogId — ідентифікатор тварини.
      2. Авторизація
      Система виконує:
      • перевірку наявності заголовка Authorization,
      • валідацію JWT-токена.
      Якщо токен невалідний:
→ повертається 401 Unauthorized → процес завершується.
      3. Запуск бізнес-логіки
      При успішній авторизації викликається server-side логіка обробки запиту.
      4. Перевірка існування тварини
      Система виконує SQL-запит:
      SELECT UserId FROM Animals WHERE Id = dogId
      Якщо тварину не знайдено:
→ повертається 404 Not Found → завершення.
      5. Перевірка прав власності
      Отриманий UserId порівнюється з id з JWT.
      Якщо IDs не збігаються:
→ повертається 403 Forbidden (користувач не є власником тварини).
      6. Перевірка відсутності привʼязаного пристрою
      Система виконує:
      SELECT * FROM SmartDevices WHERE DogId = dogId
      Якщо пристрій вже існує:
→ повертається 400 BadRequest (“Пристрій вже існує”).
      7. Успішне створення пристрою
      Якщо всі перевірки пройдені:
      • система створює новий SmartDevice,
      • встановлює параметри:
      o LastLatitude = 0,
      o LastLongitude = 0,
      o BatteryLevel = 100.
      Система виконує SQL-команду INSERT та повертає:
      → 201 Created з ID створеного пристрою.
      8. Завершення процесу
      Усі гілки (успіх або помилки) сходяться у точку завершення.

      Controller → Database:
      SELECT UserId FROM Animals WHERE Id = dogId
      4. Перевірка прав доступу
      Controller перевіряє:
      dog.UserId === decodedToken.id
      5. Перевірка дублювання пристрою
      SELECT * FROM SmartDevices WHERE DogId = dogId
      
      6. Створення пристрою
      INSERT INTO SmartDevices (...)
      7. Повернення відповіді
      Контролер повертає:
      201 Created + { id: newDeviceId }
